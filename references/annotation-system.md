# Semantic Annotation System

## 核心原則

最終文內圖不是「一張漂亮底圖加幾個裝飾文字」，而是兩個互補層次：

- **場景層**負責讓抽象內容變成可見的物理動作、路徑、角色與結果。
- **認知標註層**負責指出讀者應該看懂的判斷、名稱、數字、階段與轉折。

圖像模型不得直接負責繁中排字。先生成無字底圖，逐張看圖後再用程式後製文字。

## 預設輸出合約

每張 still 成品預設包含：

- 1 個 `headline`：一句核心判斷。
- 3–6 個 `labels`：短標註或階段名。
- 每個 label 都有一條手繪感 callout line 與 target dot，指向底圖中的實際物件。
- 全部文字面積通常不超過畫面的 30–35%。
- 底圖、標籤紙片、連線、字體與色彩語意在同篇文章內一致。

## 如何寫 headline

headline 不是文章標題、段落標題或圖表類型，而是這張圖要留下的判斷。

好例子：

- `小而專精，取代全面依賴`
- `漏洞不是猜出來，是層層證明`
- `分歧不是噪音，是升級訊號`
- `90% 留在小模型，10% 才升級`

壞例子：

- `工作流程`
- `系統架構圖`
- `重點整理`
- `這張圖說明了模型如何運作`

規則：

- 繁中建議 8–20 個字；英文建議 4–12 個詞。
- 優先使用「判斷、對比、因果、限制或結果」。
- 不重複圖下 caption。
- 不加句號，避免完整長句。
- 不使用沒有文章依據的誇張結論。

## 如何寫 labels

每個 label 必須符合三個條件：

1. **有文章依據**：名稱、數字與說法可在原文找到或直接推導。
2. **有畫面對象**：能指向一個實際可見的模型、人物、路徑、文件、關卡或結果。
3. **有認知價值**：不是把顯而易見的物件重新命名，而是幫助讀者理解它在段落中的角色。

建議：

- 繁中 2–12 個字；專有名詞可稍長。
- 一張圖 3–6 個，流程型畫面最多 7 個。
- 階段名稱可用單詞；判斷型標註用短片語。
- 數字必須保留單位、百分比或名稱，例如 `16 個 CVE`、`5B 活躍參數`。
- 使用台灣繁體中文與台灣用詞。

禁止：

- 泛用詞：`重點`、`流程`、`結果`、`系統`、`資料`。
- 冗長說明、完整段落、FAQ 式問答。
- 把 caption 拆成六段貼回圖內。
- 指向畫面中不存在或難以辨識的物件。
- 為了湊數而重複同一意思。

## 色彩語意

預設 accent 名稱與用途：

- `ink`：中性結構、輪廓、一般物件。
- `terracotta`：主角、核心模型、主要行動。
- `ochre`：主流程、路徑、規模、常規工作。
- `sage`：驗證、修補、安全結果、完成狀態。
- `indigo`：通用模型、基礎設施、對照組、次要系統。
- `brick`：風險、警告、攻擊、分歧、升級案件。

同一概念在同篇文章中不要換色。例如 `sage` 已代表安全結果，就不要在下一張拿來代表危險。

## 紙片與字體

標註視覺預設：

- 暖米色不規則紙片，細褐色邊線。
- 很淡的短陰影，方向跟底圖一致。
- 上方可有一小段半透明紙膠帶。
- 下緣使用 accent 色的乾刷線或短底線。
- callout line 略有手繪抖動，末端有小圓點。
- headline 比 labels 大一級，但不能像海報主標。
- 使用可讀的 CJK 字型；可以有手寫感，但不可犧牲辨識度。
- 不在 repository 內附帶或分享字型檔。

1600×900 基準建議：

- headline：36–46 px。
- labels：26–34 px。
- 連線：3–5 px。
- target dot：5–7 px 半徑。
- 標籤紙片與文字之間保留 12–24 px padding。

渲染器會依實際圖片寬度等比例縮放。

## 座標規則

manifest 使用 0–1 正規化座標：

- `x`、`y`：標籤紙片左上角。
- `target_x`、`target_y`：callout line 指向的物件位置。
- 座標以最終圖片完整寬高為基準。

範例：

```json
{
  "text": "5B 活躍參數",
  "x": 0.46,
  "y": 0.27,
  "target_x": 0.58,
  "target_y": 0.51,
  "accent": "terracotta",
  "font_size": 34,
  "angle": 1
}
```

## 語意先定、座標後定

生成前：

- 先從文章寫好 headline 與 labels 草案。
- 底圖 prompt 只要求預留 3–6 個安靜區，不放實際文字。

生成後：

1. 逐張查看底圖。
2. 確認每個 label 要指的物件真的存在。
3. 根據空白區更新 `x/y`。
4. 根據物件位置更新 `target_x/target_y`。
5. 將 `layout_status` 從 `draft` 改成 `final`。
6. 執行 annotation renderer。
7. 檢查最終成品，而不是只檢查 JSON。

不要在生成前死鎖精確座標，因為模型實際構圖可能偏移。

## 版面安排

- headline 優先放在上方或大面積安靜區。
- label 紙片靠近對應物件，但不要貼住主體。
- 連線應短、清楚、少交叉。
- 避開人物臉部、手部、主物件中心、路徑交會點與裁切邊緣。
- 左右兩側都有資訊時，可用不同 accent 區分，而不是用大量框線。
- 流程畫面可沿路徑依序放階段名，但不能像正式流程圖節點。
- 同張圖不要全部標籤都水平整齊排列，保留輕微手工感。
- 文字仍應服從場景；不能讓圖退化成一張簡報。

## 何時減少文字

若出現以下情況，先減標註，不要縮到難以閱讀：

- callout 線彼此大量交叉。
- 文字覆蓋主體或路徑。
- 同一資訊已由 headline 說完。
- 標籤只是重複 caption。
- 行動裝置縮圖後無法閱讀。

保留順序：

1. 核心判斷 headline。
2. 最重要的名稱或數字。
3. 因果轉折或結果。
4. 次要階段名稱。

## 後製命令

```bash
python3 scripts/annotate_images.py \
  path/to/manifest.json \
  --input path/to/images/raw \
  --output path/to/images \
  --force
```

若自動找不到可顯示繁中的系統字型：

```bash
python3 scripts/annotate_images.py \
  path/to/manifest.json \
  --input path/to/images/raw \
  --output path/to/images \
  --font /path/to/cjk-font.ttc \
  --force
```

## 失敗判斷

直接修正 annotation plan：

- 錯字、簡繁混用或數字不符原文。
- headline 只是段落標題，沒有判斷。
- label 指錯物件或線端落在空白處。
- 文字遮住主要人物、主體或關鍵路徑。
- 標籤太多、太整齊、太像 PPT。
- 紙片與底圖畫風明顯不一致。
- 行動裝置縮小後主要文字不可讀。

只有底圖本身的主體、構圖或風格錯誤時才重生成底圖。
